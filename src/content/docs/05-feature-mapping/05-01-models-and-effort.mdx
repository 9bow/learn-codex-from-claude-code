## 먼저 현재 가용성을 확인한다

Claude Code에서 넘어올 때 `opus = 고성능`, `sonnet = 균형`, `haiku = 경량`처럼 모델을 단순 대응시키고 싶을 수 있습니다. 그러나 Codex의 모델명, 제공 표면, 사용 한도는 계정·플랜·API 프로젝트·클라이언트 버전에 따라 바뀝니다. 한 번 만든 고정 대응표는 빠르게 낡습니다.

Codex CLI에서는 `/model`로 현재 세션에서 선택할 수 있는 모델과 추론 수준을 확인합니다. 명령줄에서는 `codex --help`와 현재 세션 상태를 함께 확인합니다. 2026-08-28의 공식 CLI 예시는 `gpt-5.6-sol`을 보여 주지만, 이것이 모든 계정에서 같은 기본값이라는 뜻은 아닙니다.

```text
작업 난이도 · 허용 시간 · 비용/사용 한도
                    │
                    ▼
       현재 계정의 모델 선택기에서 후보 확인
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
  짧고 반복적인 작업       설계·리뷰·복잡한 디버깅
  낮은 추론 수준부터        충분한 추론 수준과 검증
```

## 추론 수준(reasoning effort)

Codex는 모델이 지원하는 범위 안에서 추론 수준을 선택할 수 있습니다. 낮은 수준은 짧은 수정이나 반복 작업에, 높은 수준은 복잡한 설계·리뷰·원인 분석에 적합할 수 있습니다. 단, 수준이 높다고 항상 더 좋은 결과가 나는 것은 아닙니다. 명확한 범위와 테스트가 없는 작업에서는 추론 시간만 늘고 결과 확인은 여전히 어려울 수 있습니다.

```toml
# 사용자 설정의 예시
model_reasoning_effort = "medium"
```

```bash
# 현재 선택 가능한 값은 /model에서 확인한 뒤 사용합니다.
codex --model gpt-5.6-sol -c model_reasoning_effort='"high"' \
  "변경 범위와 테스트 기준을 지키며 이 모듈을 검토해줘"
```

| 작업 | 출발점 | 반드시 함께 할 일 |
| --- | --- | --- |
| 파일 한두 개의 명확한 수정 | 낮음 또는 중간 | 테스트·린트 실행 |
| 낯선 코드 탐색 | 중간 | 읽을 범위와 산출물 지정 |
| 보안·설계 리뷰 | 중간 또는 높음 | diff 범위와 리뷰 기준 지정 |
| 병렬 하위 작업 | 작업별로 별도 선택 | 비용과 결과 합치기 계획 수립 |

## 모델보다 먼저 고정할 것

팀 운영에서 중요한 것은 "항상 어떤 모델을 쓸지"보다 다음을 재현 가능하게 만드는 일입니다.

1. `AGENTS.md`에 테스트·리뷰·보안 제약을 적습니다.
2. 작업 요청에 파일 범위와 완료 기준을 넣습니다.
3. 모델 또는 추론 수준을 바꿨을 때 같은 검증 명령으로 결과를 비교합니다.
4. 플랜과 모델 가용성이 바뀌면 문서의 모델명 표를 갱신하기보다 공식 문서와 선택기로 확인합니다.

로컬 open-source provider를 검토할 때는 `--oss`처럼 별도 경로가 있다는 점도 구분합니다. 이는 ChatGPT 인증 모델과 같은 품질·권한·도구 가용성을 보장하는 대체 경로가 아닙니다.

## 핵심 정리

- Claude와 Codex의 모델을 1:1로 고정 대응시키지 않습니다.
- `/model`과 현재 세션 설정으로 실제 가용 모델·추론 수준을 확인합니다.
- 추론 수준은 작업 난이도와 검증 가능성에 맞춰 선택합니다.
- 팀 품질은 모델명보다 명확한 지침, 좁은 범위, 반복 가능한 검증에서 나옵니다.
